# 이슈·브랜치 지침서 — 모든 브랜치는 이슈에서

브랜치는 **반드시 GitHub 이슈에서 만들고 연결**한다. 이슈가 "왜 시작했고 어디까지 됐는지"의 단일 창구가 되게 하기 위해서다. 규칙 요약은 [loop.md §브랜치·이슈](loop.md)에 있고, 이 문서는 **판단 흐름·명령·강제 장치**를 담는다.

## 규칙 (1이슈 = 1브랜치 = 1성격)

| 상황 | 이슈 | 브랜치 |
| --- | --- | --- |
| **새 작업** | 새 이슈 | 그 이슈에서 `<접두사>/<이슈번호>-슬러그` |
| **기존 이슈 작업의 fix** (같은 기능·같은 도메인) | ❌ 새로 만들지 않음 | **기존 이슈**에서 `fix/<이슈번호>-슬러그` + 원 이슈에 코멘트 |
| **fix 중 나온 다른 성격** (공통 모듈·다른 기능·다른 도메인) | ✅ 새 이슈 (원 이슈 참조) | **새 이슈**에서 `<접두사>/<새이슈번호>-슬러그` |

- 접두사(성격): `task`·`fix`·`chore`·`docs`·`feat`·`refactor`·`style`·`deploy`. 브랜치명의 **숫자 = GitHub 이슈 번호**.
- spec은 `> **관련 태스크**: #이슈번호`(또는 `- **이슈:** #번호`)로 이슈를 가리킨다.

## fix인지 새 이슈인지 — 세 질문

1. 고치다 보니 **여러 곳이 쓰는 공통 모듈**을 바꾸게 됐나?
2. 원 이슈의 완료 조건에 **없는 기능**을 추가하게 됐나?
3. 원 작업과 **다른 도메인**을 건드리게 됐나?

하나라도 "예"면 **새 이슈**다. fix에 섞으면 원 이슈 범위가 흐려지고 공통 모듈 변경이 리뷰에서 묻힌다.

## 명령 (base = `develop`)

```bash
# 새 작업 — 이슈 먼저, 그 이슈에서 브랜치
gh issue create --repo <owner>/clause-lens --title "..." --body-file <본문>
gh issue develop <이슈번호> --repo <owner>/clause-lens --base develop --name <접두사>/<이슈번호>-슬러그
git fetch <remote> && git checkout <접두사>/<이슈번호>-슬러그

# 기존 이슈의 fix
gh issue develop <원이슈> --base develop --name fix/<원이슈>-슬러그
gh issue comment <원이슈> --body "fix: <무엇을 왜> (브랜치 fix/<원이슈>-슬러그)"

# PR 전 — 연결·체크박스 확인 (spec의 ### Acceptance가 원본, 이슈는 복사본)
pnpm issue-link          # 브랜치 ↔ 이슈 GitHub 연결 확인 (네트워크)
pnpm issue-sync          # 이슈 체크박스를 spec Acceptance에 맞춤
pnpm issue-sync --check  # 어긋나면 실패

# 머지 후 — "Closes #N"이 이슈를 못 닫는 경우가 있다
pnpm issue-sync --close  # PR이 합쳐졌는데 이슈가 열려 있으면 닫음 (사유 없는 미체크가 있으면 거부)
```

## 하네스가 강제하는 것

| 장치 | 내용 |
| --- | --- |
| 완료 게이트(`checks.sh`) | **0023부터** spec에 이슈 번호가 없으면 FAIL · **done** 태스크의 연결 spec에 **사유 없는 미체크**가 있으면 FAIL |
| `pnpm issue-link` | 현재 브랜치가 spec의 이슈에 **실제로 연결**됐는지 GitHub로 확인 (네트워크 → 게이트 밖, PR 전) |
| `pnpm issue-sync` | 완료 조건의 원본은 spec 하나, 이슈는 복사본으로 맞춤 · `--check` 어긋남 검사 · `--close` 머지 후 닫기 |

**체크박스 규칙:** 완료 조건의 원본은 spec의 `### Acceptance` 하나. 이슈는 `pnpm issue-sync`로 복사한다. done 작업은 사유 없는 미체크가 있으면 게이트가 실패한다 — 못 한 항목은 `- [ ] … (후속 #번호)`처럼 사유를 적는다.

## 한계

- 이슈 연결 여부는 GitHub에만 있어 오프라인 게이트로는 확인 불가 → `pnpm issue-link`를 PR 전에 실행.
- fix와 새 이슈의 경계(세 질문)는 사람·에이전트 판단이다. 기계가 판정하지 않는다.
- **0001~0022는 이슈 번호 요구 이전** 태스크라 면제. 0023부터 강제.
- ClauseLens spec은 아직 **단일 파일**(`NNNN-슬러그.md`). 폴더형(prd/sdd/trace 분리)은 이식 3·4에서 판단.
