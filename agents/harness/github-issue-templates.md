# GitHub 이슈 템플릿 정리 규칙

사용자가 `feat 템플릿으로 정리해줘`, `fix 템플릿으로 정리해줘`, `refactor 템플릿으로 정리해줘`처럼 요청하면,
에이전트는 **변경된 소스코드 기준**으로 GitHub 이슈 초안을 작성함.

## 목적

- 변경사항을 나중에 PR, 배포 노트, 작업 기록으로 재사용할 수 있게 하는 목적.
- 사람이 따로 문장을 만들지 않아도 현재 diff에서 핵심을 추출해 이슈 형태로 남기는 목적.
- 템플릿 이름이 달라도 입력 근거는 항상 **코드 diff와 관련 문서 변경**이라는 원칙.

## 트리거 문구

아래 표현은 모두 같은 의미로 처리함.

- `feat 템플릿으로 정리해줘`
- `feature 템플릿으로 정리해줘`
- `refactor 템플릿으로 정리해줘`
- `fix 템플릿으로 정리해줘`
- `style 템플릿으로 정리해줘`
- `docs 템플릿으로 정리해줘`
- `deploy 템플릿으로 정리해줘`

## 입력 근거 우선순위

이슈 초안은 아래 순서로 근거를 잡음.

1. 작업 트리의 변경 파일 (`git diff`)
2. 스테이징된 변경 (`git diff --cached`)
3. 마지막 커밋 차이 (`git show --stat --patch --summary HEAD`)
4. 연결된 spec / feature / 문서 맥락

코드 변경이 없고 문서만 바뀌었으면 `docs` 또는 `deploy` 성격으로 해석함.
근거가 없으면 추측하지 말고 사용자에게 어떤 변경을 기준으로 할지 묻는 원칙.

## 템플릿 선택 규칙

- `feat` / `feature`: 사용자 가치가 늘어나거나 새 동작이 생긴 경우
- `refactor`: 외부 동작은 유지하고 구조·책임·중복을 개선한 경우
- `fix`: 버그, 회귀, 예외 처리 누락, 잘못된 상태를 수정한 경우
- `style`: UI, 카피, 레이아웃, 디자인 시스템, 시각 일관성 변경
- `docs`: README, 운영 문서, 에이전트 문서, 가이드 변경
- `deploy`: 배포 설정, 환경, 릴리스, 채널, 인프라 반영 작업

하나의 diff에 여러 성격이 섞여 있어도, 사용자가 지정한 템플릿을 우선함.
다만 지정한 템플릿과 실제 변경이 강하게 어긋나면 그 점을 한 줄로 명시함.

예:
- "현재 diff는 기능 추가보다 버그 수정 성격이 강하지만, 요청대로 feature 템플릿으로 정리함."

## 출력 규칙

- 결과는 **바로 GitHub issue에 붙여넣을 수 있는 형태**로 작성함.
- 템플릿 필드 이름은 `.github/ISSUE_TEMPLATE/*.yml`의 항목과 맞춤.
- 추상적인 표현보다 **변경 파일과 실제 동작 변화**를 기준으로 씀.
- 사용자가 별도 요청하지 않으면 과장하지 않음.
- 모르는 내용은 채우지 말고 `확인 필요`로 둠.
- 각 템플릿 초안 하단에 `커밋메시지(한글)` 항목을 추가함.
- 모든 본문 문장은 가능하면 동사 어미 대신 **명사형 종결**로 작성함.

## 문체 규칙

- 기본 종결은 `추가`, `정비`, `개선`, `필요`, `목적`, `상태`, `위험`, `확인 필요` 같은 **명사형 종결** 사용.
- `합니다`, `입니다`, `됩니다`, `있습니다` 같은 존댓말 종결 미사용.
- 가능하면 개조식 나열보다 **짧은 명사형 문장** 우선 사용.
- 완료 조건, 체크리스트처럼 목록이 필요한 곳만 불릿 사용.

## 템플릿별 출력 골격

### Feature / feat

- 요약
- 문제 / 배경
- 제안하는 변경
- 완료 조건
- 우선순위

### Refactor

- 대상
- 이유
- 범위
- 리스크 / 확인 포인트
- 우선순위

### Fix

- 문제 현상
- 재현 방법
- 기대 동작
- 영향 범위
- 심각도

### Style

- 현재 상태
- 원하는 방향
- 참고 자료
- 대상 영역

### Docs

- 문서 문제
- 필요한 변경
- 대상 독자

### Deploy

- 배포 대상
- 변경 내용
- 사전 체크리스트
- 롤백 / 대응 계획
- 환경

### 공통 추가 항목

- 커밋메시지(한글)

## 작성 절차

1. 변경 파일과 diff를 읽음.
2. 변경의 성격을 한 문장으로 요약함.
3. 요청된 템플릿에 맞는 필드만 채움.
4. 코드에 없는 내용은 추정하지 않음.
5. 모든 문장을 명사형 종결로 다듬음.
6. 변경 성격을 반영한 `커밋메시지(한글)` 1개를 함께 제안함.
7. 사용자에게 초안을 반환함.

## 짧은 예시

사용자:
`feat 템플릿으로 정리해줘`

에이전트:

```md
요약
- 분석 결과 화면의 하이라이트 목록 접기/펼치기 기능 추가

문제 / 배경
- 결과 항목 증가에 따른 화면 밀도 상승 및 핵심 조항 탐색 난이도 증가

제안하는 변경
- 결과 카드 섹션의 접기/펼치기 상태 추가 및 기본 동작 정리

완료 조건
- 하이라이트 목록을 접고 펼칠 수 있다
- 기존 분석 결과 렌더링이 깨지지 않는다
- 상태 전환 시 앱 오류가 발생하지 않는다

우선순위
- Medium

커밋메시지(한글)
- 하이라이트 목록 접기 기능 추가
```
