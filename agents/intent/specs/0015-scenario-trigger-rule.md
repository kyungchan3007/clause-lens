## PRD (왜/무엇)

### 1. 문제
`loop.md §테스트 필수`가 "매 코드 태스크 e2e 무조건"으로 뭉툭해, **기능 변화와 시나리오의 동기화 기준이 불명확**. 기능이 바뀌어도 시나리오를 안 고치면 코드와 어긋나 썩는다(assert 깨짐 / 헛통과). placeholder 시나리오 문제(0013/0014에서 겪음)의 구조적 재발.

### 2. 목표
- 기능 생명주기(추가/변경/삭제)에 시나리오 생명주기를 묶는 **트리거 규칙**을 지침에 명문화.
- VERIFY self-check + memory에 강제 지점 추가.

### 3. 비목표
- 시나리오 내용 자체(S9~S15 백필)는 이 태스크 밖(후속). 여기선 **규칙만**.

## SDD (어떻게)

### 고려한 대안·트레이드오프 (핵심 결정)
- **A. 규칙 + 첫 적용(S9~S15 백필)을 한 PR로** — 편의상 PR 1개. 그러나 거버넌스 변경과 기능 범위 산출물이 한 리뷰에 뭉개지고, 되돌리기 독립성이 없으며, "하면서 규칙을 만든" 인과가 됨.
- **B(채택). 규칙 전용 PR 먼저 → 머지 후 백필** — 관심사 분리·원자적 PR·**DEFINE→BUILD 순서(정의가 적용보다 먼저)**·독립 revert·#45(지침 전용 PR) 선례 일치. 트레이드오프는 PR 1개 증가뿐 → 오래 남는 문서라 정석 값어치를 함.
- 사용자 확인: "어떤 게 정석?" → B가 정석, 채택.
