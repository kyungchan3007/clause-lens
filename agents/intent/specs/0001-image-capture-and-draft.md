## PRD

### 문제
사용자가 계약서를 분석하려면 먼저 여러 장의 이미지를 앱에 들여와야 한다. 촬영/갤러리 선택, 페이지 순서 변경·삭제·교체를 서버 업로드 **이전에** 자유롭게 할 수 있어야 한다.

### 목표
- G1. 카메라 촬영과 갤러리 선택으로 페이지를 추가한다.
- G2. 여러 페이지를 순서 변경·삭제·교체할 수 있다.
- G3. 서버 전송 전 상태를 클라이언트 **Draft**로만 관리한다.

### 목표가 아닌 것
- N1. S3 업로드·Presigned URL 연동 (스펙 0002에서 다룸).
- N2. OCR 요청·결과 표시 (별도 스펙).

### 사용자 흐름
1. 홈에서 "촬영" 또는 "갤러리" 선택 → 페이지가 Draft에 추가된다.
2. 페이지 목록에서 드래그로 순서 변경, 스와이프로 삭제, 탭으로 특정 페이지 교체.
3. "분석하기"를 누르면 Draft가 업로드 단계로 넘어간다(0002).

### 성공 지표
- 3장 이상의 페이지를 추가·재정렬·삭제하는 동안 앱이 상태를 잃지 않는다.

### 제약
- Expo v57 이미지/카메라 API만 사용 → https://docs.expo.dev/versions/v57.0.0/
- 클라이언트 Draft와 서버 기준 상태를 물리적으로 합치지 않는다. → [architecture.md](../../context/architecture.md)

### 미해결 질문
- Q1. 클라이언트 상태는 Zustand로 갈 것인가(README에 "예정")? → SDD에서 결정.

## SDD

### 접근 방식
페이지 Draft를 클라이언트 상태 store에 배열로 보관: `{ id, localUri, order }[]`. 서버 개념(imageKey, revision)은 이 단계에서 존재하지 않는다.

### 고려한 대안
| 대안 | 장점 | 단점 | 채택? |
| --- | --- | --- | --- |
| Zustand store | README 방향과 일치, 경량 | 의존성 추가 | ✅ |
| React state + Context | 의존성 0 | 다중 화면 공유 번거로움 | ❌ |

### 영향받는 코드
- 신규: 페이지 Draft store, 촬영/선택 화면, 페이지 목록 컴포넌트.
- 신규 의존성: `zustand`, Expo image picker/camera 모듈 (v57 호환 확인 필수).

### 데이터 / 계약
이 단계는 순수 클라이언트. 서버 계약 없음. Draft 항목 형태만 내부적으로 고정.

### 위험과 완화
- R1: Expo v57에서 카메라 API 시그니처 변경 가능 → 착수 전 버전 문서 확인.

### 롤아웃 / 되돌리기
독립 화면이라 기능 플래그 없이 추가. 되돌리기는 라우트 제거로 충분.

### 검증
수동: 시뮬레이터에서 3장 추가→재정렬→삭제→교체. 자동: typecheck 게이트.

## Acceptance Criteria

### 기능
- [ ] **AC1** — Given 빈 홈, When 촬영 완료, Then 페이지 목록에 1개 항목이 order=0으로 추가된다.
- [ ] **AC2** — Given 3개 페이지, When 2번째를 삭제, Then 남은 항목의 order가 0,1로 재정렬된다.
- [ ] **AC3** — Given 특정 페이지, When 교체 선택, Then 해당 항목의 localUri만 바뀌고 order·id는 유지된다.
- [ ] **AC4** — Draft 상태는 앱을 다른 탭으로 옮겼다 돌아와도 유지된다.

### 비기능
- [ ] `bash agents/harness/evals/checks.sh` PASS
- [ ] iOS·Android 시뮬레이터에서 크래시 없음
- [ ] 서버 통신 코드 없음(이 스펙 범위)

### 범위 밖
- S3 업로드, Presigned URL, OCR 요청/결과.
